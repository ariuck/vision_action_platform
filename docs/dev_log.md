# 개발 기록

만들면서 막혔던 것과 어떻게 풀었는지 적어 둔다.

## 1. 서비스와 학습의 특징 계산이 같은지 확인

- 문제: 서비스(FastAPI)에서 특징을 다시 계산하는데, 학습 때와 조금이라도 다르면 정확도가 떨어진다.
- 확인: `ai_service/tools/check_feature_parity.py`로 같은 영상에서 서비스 특징과 학습 시퀀스 CSV를 비교했다.
- 결과: 1,350개 특징의 최대 차이 0.000002 (반올림 수준). 그대로 사용.

## 2. 업로드하자마자 작업이 실패 (`No module named 'packaging'`)

- 문제: 로컬에서 영상을 올리니 바로 FAILURE가 뜨고 에러 코드가 QUEUE_UNAVAILABLE이었다.
- 원인: backend 가상환경에 Celery 실행에 필요한 `packaging` 패키지가 빠져 있었다. 작업 등록 중 예외가 나서 대기열 실패로 처리됐다.
- 해결: `packaging==26.4`를 설치하고 `backend/requirements.txt`에 버전을 적었다.
- 결과: 같은 영상 두 개로 다시 확인

| 영상 | 예측 | Confidence | 전체 처리 시간 |
|---|---|---|---|
| S05_A007_T01 (바닥에 앉기) | A007 바닥에 앉기 | 0.72 | 20.7초 |
| S05_A016_T03 (뒤로 넘어지기) | A016 뒤로 넘어지기 | 0.81 | 13.7초 |

FastAPI에 직접 보냈을 때와 같은 값이 나와서 Django → Celery → FastAPI → DB 저장까지 흐름이 맞는 것을 확인했다. (로컬 GPU 기준, 컨테이너는 CPU라 더 느릴 수 있음)

## 3. 좁은 화면에서 표가 찌그러짐

- 문제: 브라우저 폭이 좁으면 이력 표 글자가 한 글자씩 줄바꿈됐다.
- 해결: 표를 `.table-wrap`(가로 스크롤)으로 감싸고, 800px 이하에서 상단 메뉴가 줄바꿈되게 했다.

## 4. 컨테이너에서 CSS가 안 나오는 문제 대비

- DEBUG=0이면 Django가 static 파일을 주지 않는다. gunicorn으로 띄울 것이라 `whitenoise`를 넣고 이미지 빌드 때 `collectstatic`을 실행하게 했다.
- 컨테이너로 띄운 뒤 `/static/css/app.css`가 200으로 나오는 것 확인.

## 5. Docker Compose로 5개 컨테이너 실행

- `docker compose up -d --build` 후 postgres, redis, fastapi, django, celery 모두 healthy.
- 로컬에서는 확인용으로 Celery를 바로 실행(eager)했지만, 컨테이너에서는 실제로 Redis 대기열을 거친다. 업로드하면 바로 202와 PENDING이 오고, Worker가 처리한 뒤 SUCCESS로 바뀌었다.

| 영상 | 예측 | Confidence | 전체 처리 시간 (CPU) |
|---|---|---|---|
| S05_A007_T01 | A007 바닥에 앉기 | 0.71 | 30.8초 |
| S05_A016_T03 | A016 뒤로 넘어지기 | 0.81 | 21.7초 |

- 컨테이너는 GPU 없이 CPU로 돌려서 로컬(GPU)보다 약 1.5배 느렸다. Confidence는 소수 둘째 자리에서 조금 다르지만 예측 동작은 같다.

## 6. 재시작 후 데이터 유지

- `docker compose down` → `docker compose up -d` 후에도 작업 2개, 예측 2개, 업로드 영상 경로가 그대로 남았다.
- PostgreSQL 데이터와 업로드 영상을 이름 있는 볼륨(`postgres_data`, `media_data`)에 두었기 때문이다. `down -v`를 쓰면 볼륨까지 지워지니 주의.

## 7. IP Webcam 첫 테스트: "사람을 찾지 못했습니다"

- 문제: 휴대폰(DroidCam)을 연결하고 분석을 눌렀더니 8초 동안 481 Frame은 들어왔는데 결과가 "영상에서 사람을 찾지 못했습니다"였다.
- 원인: 처음 만든 화면에는 카메라 영상이 안 보였다. 버튼을 누르면 서버가 몰래 8초를 녹화하는 구조라, 언제 녹화되는지도, 내가 화면 안에 있는지도 알 수 없었다.
- 확인한 것: Celery 컨테이너에서 카메라 주소로 Frame을 읽어 보니 1280×720으로 잘 들어왔다. 카메라 연결 자체는 문제가 없었다.
- 해결: 교재 화면처럼 왼쪽에 카메라 미리보기, 오른쪽에 분석 상태·결과가 보이게 바꿨다 (8번).

## 8. 카메라 미리보기와 녹화가 같이 안 되는 문제

- 문제: 미리보기(Django)와 녹화(Celery)가 각각 카메라에 접속하려고 했다.
- 확인: 컨테이너에서 같은 주소로 연결 두 개를 동시에 열어 봤다. 첫 번째는 되는데 두 번째는 0.2초 만에 실패했다. DroidCam은 한 번에 한 곳만 받는다.
- 해결: 카메라 연결은 전체에서 하나만 열고(Redis 잠금), 읽은 Frame을 JPEG로 Redis에 계속 덮어쓴다. 미리보기와 녹화는 둘 다 Redis에서 Frame을 꺼내 쓴다 (`backend/analyses/camera_hub.py`).
  - 아무도 안 보고 있으면 6초 뒤 연결을 스스로 닫는다.
  - 카메라 주소는 서버만 알고 브라우저에는 이름만 보인다.
- 같이 추가한 것
  - 미리보기 위에 사람 뼈대 표시 (FastAPI `POST /pose/frame`, 사진 1장 관절만 추출, DB 저장 없음)
  - 진행 단계 표시: 대기 → 영상 수집 → AI 분석 → 완료 (`AnalysisJob.stage` 필드 추가)
  - 시작 버튼을 누르면 3·2·1 뒤 녹화, 녹화 중 남은 시간 표시

## 9. OpenCV 카메라 연결 오류 (`Sequence item with index 1 has a wrong type`)

- 문제: 카메라 연결 코드를 바꾼 뒤 미리보기가 안 나오고 로그에 위 오류가 찍혔다.
- 원인: `cv2.VideoCapture(url, CAP_FFMPEG, [옵션, 값])`의 값 자리에 `10.0 * 1000`처럼 실수를 넣었다. OpenCV는 정수만 받는다.
- 해결: `int(...)`로 바꿨다.

## 10. 카메라 주소를 화면에서 등록

- 요청: 카메라를 바꿀 때마다 `.env`를 고치지 않고, 화면에서 주소를 넣어 원하는 카메라로 연결하고 싶었다.
- 고민: 주소를 아무거나 받으면 서버가 인터넷 사이트나 컨테이너 안의 DB·Redis로 접속하는 통로가 될 수 있다.
- 해결: 화면에서 이름·IP·포트·경로를 넣어 등록하되 다음만 허용했다 (`backend/analyses/camera_registry.py`, `Camera` 모델).
  - http 주소, IP는 숫자로만
  - `CAMERA_ALLOWED_NETWORKS`(기본 192.168.0.0/16) 안의 주소만 → 같은 Wi-Fi의 휴대폰은 되고 8.8.8.8, 127.0.0.1, 172.18.x(컨테이너망), `redis` 같은 이름은 막힘
  - 삭제는 등록한 사람이나 관리자만
- 테스트로 위 주소들이 실제로 막히는지 확인했다 (`CameraViewTests`).

## 11. 카메라로 해 보니 성능이 낮음 (문제 발견)

카메라로 4번 분석한 결과를 DB에서 꺼내 봤다.

| 작업 | 잡힌 사람 | 결과 |
|---|---|---|
| #4 | 2명 | 뒤로 눕기 0.30 / 0.49 |
| #5 | 3명 | 키오스크 두드리기 0.14(판단 불확실) / 바닥에 앉기 0.30 / 0.29 |
| #6 | 3명 | 밀치기 0.21 / 바닥에 앉기 0.55 / 0.35 |
| #7 | 4명 | 옆으로 쓰러지기 0.27 / 바닥에 앉기 0.30 / 위에 앉기 0.35 / 0.35 |

보인 문제
1. **뒤에 있는 사람까지 분석됨**: 한 번에 2~4명이 잡혔다. 8초 내내 보인 사람이 "바닥에 앉기·위에 앉기"로 나왔는데, 뒤쪽에 앉아 있던 사람으로 보인다.
2. **Track ID가 끊김**: 1~4초만 보인 조각(ID 3, 5, 9)이 따로 예측돼 결과가 지저분하다.
3. **가만히 있어도 쓰러지기로 나옴**: 그냥 서 있었는데 "옆으로 쓰러지기"가 나왔다.
4. **Confidence가 0.14~0.55로 낮음**.
5. **맞았는지 판단 불가**: "수행한 동작"을 안 골라서 정답과 비교할 수 없었다.

## 12. 성능이 낮은 원인 분석

- **정상 행동 클래스가 없다**: 모델은 17개 이상행동 중 하나를 무조건 고른다. 서 있기·걷기 같은 선택지가 없어서, 가만히 있어도 가장 비슷한 이상행동을 고른다. 쓰러지기 영상들은 서 있는 자세로 시작하니 서 있는 모습과 비슷해 보였을 수 있다. → 문제 3의 원인. 정상 클래스를 넣어도 17개 동작을 맞히는 정확도는 그대로라, 문제 1·2·4와는 따로 봐야 한다.
- **8초 안에 서 있는 시간이 섞임**: 학습 영상은 동작 직전부터 직후까지만 찍혀 있다 (`action_segments.csv` 기준 영상 길이 중간값 5.4초, 앞 여유 평균 0.6초, 뒤 여유 평균 0.2초). 카메라 8초에는 준비하고 서 있는 시간이 들어가서, 30 Step으로 줄이면 동작 부분이 작아진다.
- **촬영 조건 차이**: 학습 영상과 카메라 위치·거리·배경·사람이 다르다.
- **신뢰도가 낮다고 꼭 틀린 건 아님**: 학습 평가(LOSO)에서도 평균 Confidence는 0.33이었는데 정확도는 0.75였다. 17개로 확률이 나뉘어서 원래 값이 낮게 나온다.
- 참고: 5번에서 확인한 S05 영상 0.71·0.81은 학습에 들어간 영상이라 성능 근거로 쓰면 안 된다. 처음 보는 사람 기준 성능은 LOSO 0.753이다.

## 13. 해결 계획

| 순서 | 방법 | 고치는 문제 | 필요한 것 |
|---|---|---|---|
| 1 | **동작 없음 규칙**: 움직임이 기준보다 작으면 예측 대신 "동작 없음(정상)" | 3 | 코드만 |
| 2 | **동작 구간 자르기**: 학습 때 쓴 `team_action_segments.py` 방식(관절 12개 0.1초 이동 거리 ÷ 상체 길이, 하위 5%~상위 95%의 20% 기준선, 앞뒤 0.2초 여유)으로 동작 부분만 잘라 예측 | 4 | 코드만 |
| 3 | **주인공 필터**: 화면에서 크게·오래 보인 사람만 결과로, 작거나 잠깐 보인 사람은 "배경 인물"로 접기 | 1, 2 | 코드만 |
| 4 | 테스트할 때 "수행한 동작"을 골라서 정답과 비교 | 5 | 테스트 방법 |
| 5 | 지금 카메라 위치에서 팀원 동작 추가 촬영 후 재학습 | 4 | 팀 촬영 |
| 6 | 정상 행동(서 있기·걷기·물건 보기 등) 촬영 → 18번째 클래스로 재학습 | 3 | 팀 촬영 |

- 1과 2는 같이 넣어야 한다. 구간 자르기는 영상마다 기준선을 따로 정해서, 가만히 있을 때는 작은 흔들림을 동작으로 잘라 버린다. 그래서 움직임이 충분한지 먼저 보고(1), 그다음 자른다(2).
- 넣은 뒤에는 학습 영상으로 다시 돌려 정확도가 떨어지지 않았는지 확인하고, 카메라로 "가만히 서 있기"와 "동작하기"를 비교한다.

## 14. 동작 없음 규칙·주인공 필터 기준값 정하기

**처음 생각한 주인공 기준**: 화면 높이의 25% 이상 + 2초 이상 보인 사람
→ 카메라 영상에 Track ID 박스를 그려 보니 안 맞았다. 뒤쪽 책상에 앉은 사람도 화면 높이의 37~42%로 꽤 크고 8초 내내 보였다.

**영상을 보고 다시 찾은 차이**
- 배경 인물은 화면 **왼쪽 끝에 걸쳐 잘려** 있었다.
- 책상에 앉아 있어서 **다리(발목)가 안 보였다**.
- 실제 동작한 사람은 가운데에 몸 전체가 보였다.
→ 기준에 "화면 끝에 걸친 Frame 절반 미만", "두 발목이 보인 Frame 비율"을 추가했다 (`ai_service/services/track_quality.py`).
- 사람 키는 평균 대신 BBox 높이 상위 90%를 쓴다. 누우면 BBox 높이가 줄어서 평균을 쓰면 넘어지기 영상이 작게 잡힌다.

**학습 영상 255개로 확인** (`ai_service/tools/calibrate_quality.py`, 실제 동작한 사람 기준)

| 값 | 최소 | 중간값 |
|---|---:|---:|
| 움직임 크기 | 0.428 (구토) | 1.426 |
| 키 / 화면 높이 | 0.291 | 0.609 |
| 보인 시간 | 1.62초 | 5.36초 |
| 두 발목 보인 비율 | 0.532 | 1.0 |

| 기준 | 처음 값 | 학습 영상에서 생긴 문제 | 바꾼 값 |
|---|---|---|---|
| 동작 없음 (움직임) | 0.30 미만 | 없음 (255개 모두 통과) | 0.30 유지 |
| 최소 보인 시간 | 2.0초 | S03 샷건 T03이 1.62초라 배경으로 빠짐 | **1.0초** |
| 두 발목 보인 비율 | 0.5 | 최소 0.532(위에 앉기 후면)라 여유가 너무 작음 | **0.3** |

바꾼 뒤: 학습 동작 영상 255/255가 주인공, 카메라 영상 4개는 모두 앞에 선 1명만 주인공.

- 아직 확인 못 한 것: **가만히 서 있기만 한 카메라 영상이 없다.** 동작 없음 기준 0.30이 실제 정지 상태를 잡는지는 카메라로 8초 가만히 서 있는 테스트를 해야 알 수 있다.
- 참고: 카메라 #5는 첫 1초가 90도 돌아가 있었다. 녹화 중 휴대폰 방향이 바뀐 것으로 보인다. 카메라는 고정해야 한다.

## 15. 카메라 영상 4개 전후 비교

예전 카메라 영상 4개를 새 서비스(동작 구간 모델 + 동작 없음 규칙 + 주인공 필터)에 다시 올려 비교했다.

| 카메라 | 전 (모든 사람 결과) | 후 (주인공) | 후 (배경으로 접힘) |
|---|---|---|---|
| #4 | 뒤로 눕기 0.30 / 뒤로 눕기 0.49 | 뒤로 넘어지기 0.35 | 1명 |
| #5 | 키오스크 두드리기 0.14 / 바닥에 앉기 0.30 / 0.29 | 쪼그려 물건 빼내기 0.17 | 2명 |
| #6 | 밀치기 0.21 / 바닥에 앉기 0.55 / 0.35 | 밀치기 0.21 | 2명 |
| #7 | 옆으로 쓰러지기 0.27 / 바닥에 앉기 0.30 / 위에 앉기 0.35 / 0.35 | 옆으로 쓰러지기 0.26 | 3명 |

**좋아진 것**
- 뒤에 앉은 사람 결과가 전부 배경으로 접혀서, 영상마다 실제 동작한 1명만 남았다. 뒷사람이 "바닥에 앉기·위에 앉기"로 나오던 문제가 없어졌다.

**좋아지지 않은 것**
- 주인공 예측은 거의 그대로이고 Confidence도 0.17~0.35로 낮다.
- #7은 서 있다가 바닥에 앉은 영상인데 여전히 "옆으로 쓰러지기"이고, 바닥에 앉기는 후보 3개에도 없다.

## 19. 발차기 한 번만 잘라도 확신이 낮음 → 동작 모양 자체가 다름

카메라 영상에서 발차기 한 번만 들어간 부분을 잘라 지금 서비스로 예측했다.

| 영상 | 8초 전체 | 발차기 한 번만 |
|---|---|---|
| #17 | 던지기 0.34 | 앞차기 0.27 (1.2~3.4초) / 던지기 0.37 (3.2~5.6초) |
| #16 | 던지기 0.30 | 앞차기 0.15 |
| #15 | 앞차기 0.18 | 앞차기 0.17 / 0.19 |

한 번만 넣으면 5번 중 4번 앞차기가 1등이지만 확신이 15~27%로 낮고 던지기와 거의 비슷했다. 그래서 Feature를 학습 앞차기·던지기와 비교했다.

| | 학습 앞차기 | 학습 던지기 | 카메라 발차기 |
|---|---:|---:|---:|
| 발목 속도 최대 (왼/오른) | 4.6 / 5.5 | 1.5 / 1.0 | **2.4 / 3.1** |
| 무릎 각도 평균 (작을수록 굽힘) | 166° / 165° | 173° / 173° | **173° / 172°** |
| 손목 속도 최대 (왼/오른) | 3.9 / 3.1 | 4.4 / 11.3 | 3.0 / 2.5 |

- 학습 앞차기는 **무릎을 굽혔다가 빠르게** 찼다. 카메라 발차기는 다리를 거의 편 채 들고, 발 속도가 학습의 절반 정도였다.
- 그래서 앞차기와 던지기 사이 어딘가로 보였다. 손목 속도는 오히려 앞차기에 가까워서, 팔 때문은 아니었다 (16번 추정 수정).

**정리**
- 코드로 구간 규칙을 바꾸는 건 학습 영상 전체 성능을 떨어뜨려서 하지 않는다.
- 바로 할 수 있는 것: 학습 영상처럼 **무릎을 굽혔다가 세게** 한 번 차고, 앞뒤로 가만히 서 있기.
- 근본 해결: 사람마다 동작하는 방식이 다르다. 실제 카메라 앞에서 여러 사람이 여러 강도로 한 동작을 학습에 넣어야 한다 (팀 촬영).

## 20. 왜 하필 "한손 물건 던지기"인가 / 서 있는 시간이 동작 구간에 들어감

**#18 (다시 찍은 발차기)**: 던지기 0.28, 앞차기 0.23. 동작 구간 0~7.5초.

- 발차기 순간 사진을 보니 무릎을 카메라 쪽으로 들어 올려서 허벅지가 가려졌고, YOLO가 무릎 점을 반대쪽 정강이 근처에 찍었다.
- 움직임 그래프: 처음 0~1초(자리 잡기) 1.9, 발차기(2.8초) 1.2, 서 있을 때 흔들림 0.3~0.5. 기준선이 0.34로 잡혀 흔들림까지 동작 구간이 됐다.
- 학습 정면 앞차기 5개 사진: 모두 **주먹을 든 가드 자세 + 다리를 앞으로 뻗기**. 카메라 발차기는 팔을 내리고 무릎을 드는 모양이었다.
- 정면 학습 영상 기준으로 17개 동작 평균과 비교하면 카메라 발차기는 **앞차기와 가장 비슷**했다 (거리 0.08, 던지기 0.24). 모델이 많이 보는 Feature는 BBox 가로세로 비율, 무릎·손목 높이, 무릎·팔꿈치 각도였다.
- 정리: 동작 구간에 서 있는 시간이 대부분 들어가서, 30 Step 시간표가 "팔 내리고 서 있다가 잠깐 움직임" = 학습의 던지기 모양이 됐다. 팔꿈치 평균 각도도 던지기와 같았다 (159.7° vs 159.9°, 앞차기 140.6°).
- 그리고 "녹화 끝까지 가만히 서 있으라"는 앞선 안내가 지금 규칙에서는 오히려 나빴다. 기준선이 영상마다 상대적이라 서 있는 시간이 길수록 흔들림이 동작으로 잡힌다.

**결과**: ❌ 미적용

- 서 있을 때의 0.4 정도 움직임은 떨림이 아니라 **실제 작은 움직임**(무게 중심 옮기기, 팔 조금 움직이기)이었다. 학습 영상의 가장 작은 동작(구토 0.43, 두드리기 0.44)과 같은 크기다.
- 그래서 **움직임 크기 하나로는 "카메라 앞에서 서 있기"와 "작은 동작"을 구별할 수 없다.** 교차 평가는 카메라 값부터 나빠져서 돌리지 않았다.
- 코드는 `motion_curve(..., pos_smooth_sec)` 옵션으로 남겨 두되 기본값 0(사용 안 함). 기존 결과와 같음을 다시 확인 (학습 코드와 최대 차이 0.000008).

**이 문제를 제대로 풀려면**
- 정상 행동(서 있기·무게 중심 옮기기·걷기)을 학습에 넣어 "서 있음"을 모델이 직접 배우게 하기
- 지금 카메라로 찍은 동작 영상을 학습에 넣어, 앞뒤에 서 있는 시간이 섞인 모양도 배우게 하기

## 25. 카메라 분석이 "저장된 영상 파일을 찾을 수 없습니다"로 실패

**문제**: 다른 휴대폰을 카메라로 등록해 분석하니 #38·#39가 `VIDEO_MISSING`으로 실패했다. 메시지는 "카메라에서 8.0초 동안 884개 Frame을 받았습니다"까지 나왔다. 화면에는 영상 수집이 진행 중(파랑)으로 남고 AI 분석에 ✕가 표시됐다.

**원인 확인** (Celery 로그)
```
[mpeg4] timebase 1000/110443 not supported by MPEG 4 standard,
        the maximum admitted value for the timebase denominator is 65535
VIDEOIO/FFMPEG: Failed to initialize VideoWriter
```
- 이 휴대폰은 8초에 884 Frame, 약 **110fps**로 들어왔다 (어제 휴대폰은 약 60fps).
- 저장 fps를 `받은 Frame 수 ÷ 시간` = 110.443으로 그대로 넣었는데, mp4v(MPEG-4)는 fps를 1000분의 1 단위 분수로 적고 분모가 65535를 넘으면 파일을 아예 못 만든다.
- 저장 실패를 확인하지 않아서, 다음 단계에서 "파일 없음"으로만 보였다.
- 화면은 실패한 단계를 "마지막으로 본 단계 다음 칸"에 표시해서, 영상 수집에서 실패했는데 AI 분석에 ✕가 찍혔다.

**고친 것**
- 저장 fps를 정수로 맞추고, 60fps(학습 영상과 같음)보다 많이 들어오면 시간 간격을 고르게 60fps로 솎아낸다 (`camera_hub.write_mp4`).
- 저장이 안 되면 바로 `CAMERA_SAVE_FAILED` "녹화한 영상을 저장하지 못했습니다"로 알린다.
- 화면: 오류 코드로 실패 단계를 정한다 (카메라·영상 파일 → 영상 수집, AI 서버 → AI 분석, 대기열 → 대기).
- 테스트 2개 추가: 884 Frame/8초 → 60fps 480 Frame으로 저장, 240 Frame/8초 → 30fps 그대로 (`CameraSaveTests`). 전체 23개 통과.

## 26. 카메라 높이 흉내 증강 (실패) → 코드로 할 수 있는 건 거의 다 했다

**문제**: 새 사람 영상 5개(밀치기·흔들기·꺼내기·앞으로 눕기·키오스크치기)를 다시 올려도 키오스크치기만 맞았다 (모델이 그대로라 같은 결과).

**생각**: 새 영상은 카메라가 높이 달려 내려다보는 각도다. 위에서 보면 몸이 세로로 눌려 보이니, 학습 영상을 골반 높이 기준으로 세로 0.85배·1.15배로 바꾼 증강을 넣어 보자.

| 구성 (ExtraTrees, 시드 3번 평균) | LOSO | 가장 낮은 사람 | 외부 10개 | 외부 정답 확률 |
|---|---:|---:|---:|---:|
| 지금 (증강 7가지) | 0.881 | 0.837 | 6 | 0.328 |
| + 세로 누르기·늘리기 | 0.875 | 0.830 | 6 | 0.357 |

→ ❌ 미적용. 정답 확률이 조금 올랐지만 답이 바뀐 영상은 없고, LOSO는 조금 떨어졌다.

**지금까지 시도 정리 (새 사람 영상 기준)**
- 효과 없음: 증강 9가지(반전·속도·잡음·기울임·서 있기·30fps·세로 비율), 모델 9가지, 예측할 때 증강
- 원인: 같은 동작을 **다른 방식**으로 했다 (흔들기를 팔 벌리기 대신 주먹 쥐고, 앞으로 눕기 전 8초 서 있기 등). 모델은 5명이 한 방식만 배웠다.
- 결론: 증강·모델·규칙으로 할 수 있는 건 거의 다 했다. 남은 방법은 **그 방식의 영상을 학습에 넣는 것**이다.

## 27. 분석 화면·대시보드에 쓸모 있는 정보 추가

**왜**: 결과가 동작 이름과 신뢰도 하나뿐이라, 세부 동작이 틀렸을 때 큰 방향은 맞았는지, 지금 서비스가 얼마나 잘 맞히는지 화면에서 알 수 없었다.

**분석 화면**
- 맨 위 "내 분석 요약": 분석 건수, 성공률, 평균 처리 시간, 평균 신뢰도, 정답 일치율(수행 동작을 고른 작업 기준), 많이 나온 동작 3개
- 결과 카드
  - **묶음과 묶음 확률**: 같은 묶음 동작 확률의 합 (예: 눕기·쓰러짐 100%). AI 서버가 17개 확률을 묶음별로 더해 보낸다 (`group_scores`).
  - 수행한 동작을 골랐으면 대표 예측(가장 오래 보인 주인공)과 비교해 **일치 / 같은 묶음 / 다름** 표시
  - 판단에 쓴 동작 구간(초), 영상 길이·fps·주인공 수·배경 수·AI 시간·전체 시간
- DB: `PersonPrediction`에 `action_group`, `group_scores`, `action_start_sec`, `action_end_sec` 추가. 예전 예측은 동작표로 묶음을 채웠다 (82/85, 나머지 3개는 '동작 없음').

**대시보드**
- 핵심 숫자 6개: 전체 작업(오늘·사용자 수), 성공률(실패 수), 평균 처리 시간(AI 추론), 분석한 사람(동작 없음·배경 제외), 평균 신뢰도(판단 불확실 비율), 정답 일치율
- 차트 9개: 날짜별 분석 수(완료·실패 쌓기, 14일), 동작별 예측 건수, 동작별 평균 신뢰도, 작업 상태별, 묶음별, 신뢰도 분포(20% 미만은 주황 = 판단 불확실), 실패 원인, 입력 방식별 건수·평균 처리 시간
- 표: 동작별 정답 일치(건수·일치·일치율·대신 나온 답), 자주 헷갈린 동작, 최근 작업(수행 동작·처리 시간 포함)
- 통계 계산은 `backend/analyses/stats.py`에 모았다. 전부 Django ORM 집계다.

**고친 것**
- 업로드 미리보기: 파일을 고르기 전에도 빈 영상 플레이어가 보였다. `.stage-box video {display:block}`이 `hidden` 속성을 덮어서였다.
- 대시보드: 두 칸 차트가 칸 너비를 넘겨 가로 스크롤이 생겼다. 칸에 `min-width: 0`.
